## [0.1.0] - 2026-10-20

### Added

- Initial release. One agent (`feature-flag-unwinder`) scoped to a single repo per invocation. Given a flag key and a step (`Unwind <flag> step <N>`), it executes the step inside the current working directory, verifies with `Skill(perform-preflight)`, and opens one PR against the current repo, ready for review unless a draft is requested. Step 1 removes flagged logic plus the per-repo flag definition in clients, server, ios, or android; Step 2 removes the key from server `FeatureFlagKeys` after a backward-compat gate check delegated to `Skill(computing-backward-compatibility)` (±2 month window, safe server release = last-client-with-flag.month + 3). Step 3 (LaunchDarkly archival) is manual and never automated. A server Step 1 run also removes the `FeatureFlagKeys` constant when the compat gate already passes, combining Steps 1 and 2 in one PR. The compat skill reports `server-only` for flags that never appeared in clients, ios, or android, confirms each client removal by its diff rather than by a commit existing, attributes consumers per client (an `apps/<client>/` hit marks that client, while shared code marks browser, cli, and desktop), searches only a freshly fetched `origin/main`, and returns its evidence (the commits it searched, each client's removal commit, and the release tags), which Step 2 and combined PRs show in a Backward-compatibility validation section.
- Optional Jira ticket. With a ticket (`... for PM-1234`), the PR links it and the agent comments its outcome on it, formatted as ADF in a blue info panel with the PR as a real link where the Jira tool accepts ADF (plain text otherwise), through whatever Jira access the session has, such as `bitwarden-atlassian-tools` (used in CI) or the hosted Atlassian MCP. The agent inherits the session's tools rather than naming specific MCP tools, so either works. Without one, nothing touches Jira.
- Engineer dispatch. The agent runs from an engineer's own checkout (`claude --agent bitwarden-feature-flag-unwinder:feature-flag-unwinder "Unwind pm-1234-flag step 1"`). It derives the repo from `origin`, stops early when `origin/main` has nothing to remove, does all its work in a dedicated git worktree created from a freshly fetched `origin/main` (leaving the invoking checkout untouched, which also satisfies Claude Code's isolation guard for background sessions), finds the clients, ios, and android checkouts a server run needs from the request text (`using clients at <path>`), env, or sibling directories, switches to the repo's pinned toolchain version itself (background sessions don't inherit the launcher's environment), and ends every run with a summary for the invoker.
- `dispatching-flag-cleanup` skill. "clean up feature flag pm-1234-flag" takes a flag key (or a Jira key, read for its flag), asks for the step and whether the PRs should be drafts or ready for review when the request doesn't say, asks for an optional ticket, finds the engineer's local checkouts (per-repo `*_REPO` variables, a shared root, or by asking), checks whether each has anything to remove (skipping repos where `origin/main` has no reference to the flag), checks each repo's toolchain and offers CI validation where one is missing, confirms the plan, launches one background unwinder session per repo, and then checks each launch: it stops any session that started without the agent, and points the engineer at untrusted workspaces and sessions blocked on a prompt.
- `.github/workflows/feature-flag-unwinder.yml` in `bitwarden/ai-plugins` — the single workflow that drives the agent across all target repos. Every other Wednesday at 15:00 UTC (even ISO weeks) it queries Jira for `labels = "ready-for-cleanup" AND (labels = "flagged-logic-removal" OR labels = "server-flag-removal") AND statusCategory != Done`, reads each ticket's flag and step, skips misconfigured tickets with a warning, and runs one matrix job per (ticket, repo). A manual run skips Jira and takes `flag`, `step`, an optional `jira_issue_key`, and `draft`. Step 1 runs in clients, server, ios, and android; Step 2 in server only. Each job mints a GH App token scoped to its one target repo via Azure Key Vault, checks that repo out, sets up its toolchain, and runs the agent as `bw-ghapp[bot]` on a reusable `flag-cleanup/<flag>-step-<N>` branch. Step 2 jobs also check out clients, ios, and android read-only so the compat gate can read their tags. The `FLAG_UNWINDER_DRAFT_PRS` repository variable makes scheduled PRs drafts. Nothing is installed in the target repos.
- Every PR gets the `ai-review` label, settled before `applying-pr-conventions` runs so unattended runs don't stop to ask.
- Worktree cleanup: the agent removes its worktree and local branch after a successful run, and keeps them when a run stops partway so a person can take over.
- Branch guards against clobbering human work: if the flag-cleanup branch already exists on the remote with a tip commit not authored by the agent's own git identity (`git config user.email`, `bw-ghapp[bot]` in CI), or if the open PR carries a `stop-cleanup` label, the agent stops and reports the existing PR rather than overwriting.
- CI validation mode (`... and validate with CI`, or `VALIDATE=ci`). For an engineer whose machine can't build a repo, the agent skips the local build and tests, opens the PR anyway, and says in the PR body that its CI checks are the validation.
- Build and tests must pass before any PR is opened, unless CI validation was chosen. The agent runs the target repo's canonical build + test commands (deferring to its `CLAUDE.md`) on the edited branch before committing, iterates on fixes within a bounded budget if the removal left stragglers, and aborts if verification can't be made green.
